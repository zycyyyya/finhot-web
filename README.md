## 它是什么

finhot-web 是集自动采集、AI 分析、数据质量控制与静态页面展示于一体的金融资讯站点，面向保险运营、二级市场投教和私募销售运营三类从业者。Node.js 采集引擎通过 GitHub Actions 每日更新数据，页面按业务场景组织浏览。

本仓库与 [finhot](https://github.com/zycyyyya/finhot) 相互独立：finhot-web 负责自动更新的网页产品；finhot 是供 Agent 调用的金融保险资讯查询 Skill，并提供可选 Python 离线工具。

### 知乎数据源

给保险栏目补充**从业者视角**内容：产品实测、分红实现率解读、拒赔案例、展业与合规经验。这类内容媒体源基本不产，但对保险规划师是刚需。

- 接口：`GET https://developer.zhihu.com/api/v1/content/zhihu_search`，Bearer 鉴权 + 秒级 Unix 时间戳
- 覆盖方式：接口 `Count` 上限为 10 且**不支持翻页**，所以覆盖面靠约 40 个保险向查询词覆盖（定价口径 / 产品类型 / 展业合规 / 理赔避坑 / 公司行业 / 养老财富）
- **两个必须注意的口径**：
  1. 知乎返回的 `EditTime` 是**最后编辑时间，不是首次发布**。站内以 `timeConfidence: "edited"` 标注，不冒充发布时刻。
  2. 知乎返回的 `AuthorityLevel` 实测没有区分度（超过七成结果是最高档 L4，连零赞提问也是），因此**不用于权威分层**，只作元数据留档。该源统一按 S3 对待，入选门槛最高。
- 配额保护：单次运行上限（默认 40 次查询）+ 每日累计上限（默认 800 次，按北京时间自然日计数并落盘到 `data/zhihu-usage.json`）。4 次定时运行约用 160 次，远低于平台 5000 次/天的配额；账本提交进 Git，因此手动重跑也共用同一份配额。

配置方法：在仓库 Settings → Secrets 添加 `ZHIHU_API_TOKEN`（开放平台 Access Secret）。**未配置时该数据源自动跳过，不影响发布门**，其余来源照常运行。

## LLM 评分层（可选增强）

在启发式评分之上，可启用 **LLM 双次独立打分** 作为增强层。默认关闭，配置 `DEEPSEEK_API_KEY` / `LONGCAT_API_KEY` / `SENSENOVA_API_KEY` 任一即开启。

- **预筛控成本**：启发式分 ≥ 45 才送模型，每轮上限 15 条
- **双次独立采样**：同一提示词两次调用（`temperature: 0.8`），两次都 ≥ `FINHOT_LLM_GATE`（默认 50）才入选；最终 `item.score = 平均分`，并保留两次原始分 `llmScores`
- **金融口径提示词**：`prompts/selection-score.md`，7 种金融条目类型 × 5 轴权重，强调可核验要素、口径纪律与噪声识别
- **软降级**：LLM 任何失败（超时、格式异常、余额不足）都回退启发式分，**不影响发布门**
- **多提供方**：`scripts/llm.js` 统一封装，支持 LongCat / SenseNova / DeepSeek，带 429 重试与 JSON 解析兜底

### 校准与门槛

`data/gold.jsonl` 含 31 条手工标注（分层抽样：精选 / 高分未精选 / 中档 / 噪声 / 知乎）。运行 `node scripts/eval-selection.js --llm` 可扫描门槛 40–90 输出 F1 报告。LongCat 实测 F1 75.0%（启发式 73.3%），查准率 90%。

## 从业价值评分

总分 100，五轴全部只看内容，**来源等级不进分数**：

| 维度 | 分值 | 口径 |
|---|---:|---|
| 相关性 | 30 | 是否直接涉及保险、私募、资管、银行、监管、财富管理 |
| 业务影响 | 25 | 是否影响产品销售、客户配置、投研判断、合规风险 |
| 可核验要素 | 20 | 机构名(6) + 监管文号/法规名(6) + 具体数字(5) + 明确日期(3)，**不看正文长度** |
| 时效 | 15 | 两把尺子取高者：绝对小时刻度（新闻源）+ 源自身时效窗口的相对刻度（观点源） |
| 可行动性 | 10 | 能否转化为客户沟通、投研关注、产品提醒、风险提示 |

**来源等级只决定入选门槛**——官方一手源门槛低（同一件事官方原文更值得先看），个人创作门槛高：

| 分层 | 含义 | 入选门槛 |
|---|---|---:|
| S0 | 权威原始源 | 50 |
| S1 | 结构化数据源 | 55 |
| S2 | 专业财经媒体 | 60 |
| S3 | 快讯线索 / 从业者观点 | 70 |

**噪声硬上限**（命中即压到上限以内，与来源等级无关）。规则按精度与作用域分层——「营销软文」是标题级特征，「文末有领取入口」不是，合并判定会把一篇长文误杀：

| 类型 | 上限 |
|---|---:|
| 营销与活动推广（标题级） | 20 |
| 研报领取与引流（标题级） | 20 |
| 招聘与例行人事（标题级） | 20 |
| 时间性盘点，如"晚间公告""早报"（标题级） | 30 |
| 行情播报，如"截至收盘""连板股追踪"（标题级） | 30 |
| 无口径收益宣传（正文级，发债等融资语境豁免） | 30 |
| 代理与维权案例引流（标题级） | 40 |
| 无规模的案例与合作 PR（标题级） | 40 |
| 疑似推广用语、主题性汇总（标题级） | 50 |
| 正文含引流入口（正文级，只温和压制） | 60 |

评分逻辑集中在 `scripts/scoring.js`：`TIER_GATES` 改门槛、`NOISE_RULES` 改噪声边界、各 `*_GROUPS` 改关键词，都是改数据不改流程。

## 事件归组

不同来源报道的同一件事归为一个事件。成员必须同时满足**相似度**与**时间窗**两个条件：

- **相似度**：标题 bigram 的 Jaccard 系数；若两条共享具体主体（机构/国家/指数字命中）且至少共享一个主题词，则提到锚点下限 0.62。同类栏目门槛 0.50，跨栏目 0.60。
- **时间窗**：两条资讯的发布时间相差超过 72 小时即不合并——跨越三天的事件不可能是"同一次发生"。
- **不参与归组**：日频行情播报（"截至收盘…"）与时间性盘点本身就是逐日刷新的模板，不是事件。

> 修复说明：v2.4.0 及更早版本用 `交集 / min(|A|,|B|)`（包含度）当相似度，短标题被长标题包含就会接近 1.0；又用「共同主题词 ≥ 2 就强制 0.60」提权，而同一栏目的任意两篇稿子几乎必然共享"保险/监管"这类粗主题；再叠加没有时间窗，实测出现 6 个事件顶到证据上限并横跨两个月（如"以色列股市上涨"累计 50 条）。现版本在同一语料上巨型聚类由 14 个降为 0 个，最大规模由 32 条降为 5 条。

**模型 pairwise 判定（可选）**：启发式预筛后，对模糊候选对调用 LLM 做 pairwise 判定，输出 `SAME_OCCURRENCE` / `SAME_STORY` / `UNRELATED` / `ROUNDUP`。判定结果注入 `judgedSimilarity` 表供后续归组参考，每日设调用上限防成本失控。开启方式与评分层相同（任一 LLM API Key 即可）。

**事件综述与最新进展（full 模式）**：`full` 运行时为每个事件生成一句话综述，并挂牌最新进展（日期 + 一句话）。写入 `events.json`，前端事件链直接展示。

**旧事件一次性淘汰**：换算法不够——`events.json` 保留 120 天，旧版本产生的巨型事件会被 `retainedEvents` 原样续命（实测仍有 45 个 ≥10 条证据的事件留在文件里，其中 6 个还挂在首页事件链上）。因此事件对象带上 `clusterVersion`；版本号不匹配的历史事件直接不续命。当前事件每轮都是重新聚类得出的，历史事件只负责沿用 `eventId` 与 `firstSeenAt`，丢弃它们只损失事件连续性，不会丢失任何当期事件。

## 前端展示上限与来源留底

前端列表上限 150 条。若纯按发布时间截断，时效窗口长的来源会被窗口短的新闻源整体挤出——实测知乎 40 条内容只剩 3 条进前端，等于这个数据源白接。因此截断时按来源留底（`core.limitWithSourceReserve`，默认每来源 6 条，且压缩到 `floor(上限 / 来源数)` 以内以保证留底不超上限），剩余名额再按时间补齐。分数、门槛、排序都不受影响。

同理，**补充类内容（`evidenceType: ugc_opinion`）在今日精选里的占比上限为 1/6**（24 条里最多 4 条）。UGC 在"从业价值"评分里天然占优——相关性拉满、时效靠前，而证据轴本来只有 0~8 分（没有监管文号/机构名/数字）。实测 6 条知乎内容全进精选、4 条挤进前十，只占候选池 4% 却拿走近 1/4 精选位。上限只约束"进不进精选"，不改任何一条的分数。

## 宏观参考看板

首页顶部常驻 5 项宏观指标，由数据管线每日自动维护：

- **自动刷新**：LPR 1Y / LPR 5Y（中国货币网官方接口）、10Y 美债收益率（美国财政部官网）、美元兑人民币（ECB 参考汇率）、现货黄金（gold-api.com）
- **对比口径**：涨跌对比始终标注具体基准日期（如「较9月14日 4.97% 上升」），持平同样带出基准数值（如「较7月20日 3.00% 持平」），优先取数据源自带的上一期观测——LPR 接口的历史期次、财政部 CSV 的前一交易日、ECB 汇率区间序列；无历史接口的指标则沿用上一次运行落盘的观测
- **观测日期**：每张卡片右上角标注该数值自身的观测日期（如 LPR 显示 `8/20`），避免月度指标在「较7月20日持平」的表述下被误读成数据停在 7 月
- **基准窗口**：对比基准超过 30 天即判定失效，卡片改显示「对比基准已超30天」并弃用该基准，而不是继续引用陈旧数值；LPR 为月度指标，窗口放宽至 35 天以覆盖其 30-31 天的天然间隔
- 数值合理性校验，越界或接口失败时保留上次有效值，绝不阻塞发布、不用推断值填补
- 宏观快照同时注入 AI 日报分析上下文（仅允许引用已核实数值）
- 看板只展示可自动更新的指标；非自动项（如联邦基金利率、定存利率）保留在 `data.macro` 中供 AI 上下文使用，不在首页展示

## 自动更新

北京时间每日 08:15 主运行（完整 LLM 分析），12:17、16:19、20:21 错峰保底运行（复用 AI 内容 + 增量采集），数据质量门通过后自动提交并部署。11 个来源中任一失败都不会阻塞发布（发布门只看可用源数量与覆盖率下限）。

### 调度延迟与监控

GitHub 自带的 `schedule` 是 **best-effort 派发，不是精确时钟**。本仓库 2026-09 至 2026-10 连续 40+ 次运行实测：每个槽位实际启动时间比计划晚 **5.3–6.7 小时**，且每天 4 个槽位通常只有 2–3 个真正被派发。这是平台侧行为，与站点代码无关。

因此监控（`.github/workflows/watchdog.yml` + `scripts/schedule-watch.js`）**刻意不对齐计划时刻**，只判定一件事：**最近一次成功采集距今是否超过 10 小时**（`FINHOT_STALE_MINUTES`，默认 600 分钟）。

- 判定依据直接来自 Actions API 的实际运行记录，不读 `data/alert-state.json`——后者要靠 workflow 自己提交，失败或并发推送被拒时会滞后。
- 超过阈值 → 创建或刷新 `[finhot-alert]` Issue；恢复正常 → 自动关闭并留言。
- 单次运行的延迟阈值由 `FINHOT_SCHEDULE_DELAY_MINUTES` 控制（线上 8 小时）；低于它的延迟属常态，不告警。

> 历史教训：初版监控按「计划时刻 + 4 小时 grace」判定槽位是否缺失。grace（4h）小于实测延迟（5–7h），于是每一个被检查的槽位都必然判定为缺失，自 2026-09-21 起连续 11 天误报（Issue #34）。

## 数据质量

发布门（`scripts/health.js` 的 `DEFAULT_THRESHOLDS`，可用 `FINHOT_MIN_*` 环境变量覆盖）：

| 门槛 | 默认值 | 含义 |
|---|---:|---|
| 可用来源数 | ≥ 3 | 本次运行至少 3 个来源拿到可用内容 |
| 来源覆盖率 | ≥ 0.30 | 可用来源 / 总来源 |
| 有效条目数 | ≥ 20 | 允许进入前端的条目下限 |
| 相对上次条数 | ≥ 40% | 防止一次失败运行把首页清空 |
| 最新条目时效 | < 72 小时 | 整站最新一条必须足够新 |

其余自检：

- 证据引用悬空 = 0
- 近似标题去重
- 发布时间可信化（无时间不冒充当日；知乎编辑时间单独标注，不当作发布时间）
- 每条资讯记录命中的噪声限制与入选门槛，可逐条复核评分依据
- AI 内容经结构/枚举/长度/证据 ID 四重校验
- 本地自检：`npm run check`（18 个脚本语法检查 + 15 个测试文件，全部使用本地替身、不访问外部服务）
